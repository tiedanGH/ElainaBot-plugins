# LGTBot 游戏问答

@机器人提问 LGTBot 桌游的规则、玩法、计分与结算，AI 现场检索 LGTBot 源码后带出处作答。

与 **AI 聊天陪伴**、**AI 开发助手** 完全独立：自己的配置、自己的上下文库、自己的限流，
共用的只有 `modules/ai_llm` 这一个模型底座。

---

## ⚠️ 部署前必读：必须做 bot 绑定

默认触发方式 `at` 注册的是 `.*` + `block=True` 的兜底 handler。而 LGTBot 把玩家的
**所有游戏输入**靠 `priority=-100` 的「LGTBot 消息派发」兜底送进 C++ 引擎
（`plugins/LGTBot_ElainaBot/mod/dispatcher.py`）。

`block` 在**匹配阶段**就 `break`（`core/plugin/_dispatch.py:269`），handler 函数体根本
来不及执行。所以两个插件跑在同一个 bot 上时，本插件会把游戏派发整条掐断，**所有对局失联**。

框架的 bot 白名单检查在 block 判定**之前**（`core/plugin/_dispatch.py:231`），因此：

> 到「插件管理 → bot 绑定」，把 **LGTBot游戏问答** 绑到问答 bot、
> **LGTBot_ElainaBot** 绑到游戏 bot。两者互不可见，block 就伤不到 LGTBot。

未绑定且检测到 LGTBot 也加载时，插件加载会打 WARNING，面板顶部显示红色横幅。
不想绑定就把触发方式改成 `prefix`（只有 `/问 xxx` 才命中并拦截）。

## 安装

1. 放进 `plugins/`，框架自动加载。
2. 启用 `modules/ai_llm`（AI LLM 服务），在其面板配好接口、Key 和模型。
   本插件**不保存任何密钥**。
3. 做上面的 bot 绑定。
4. 打开侧边栏「LGTBot 问答」页，确认「可检索范围」全部就绪。

源码目录默认自动定位同框架的 `plugins/LGTBot_ElainaBot`。`lgtbot/` 是 git submodule，
没拉取时面板会报红，服务器上执行：

```bash
git submodule update --init --recursive lgtbot
```

## 使用

| 指令 | 说明 |
|---|---|
| `@机器人 <问题>` | 直接提问（`at` / `both` 模式） |
| `/问 <问题>` | 前缀提问（`prefix` / `both` 模式） |
| `/问答` | 查看用法 |
| `/问答 清空` | 清空自己的追问上下文 |
| `/问答 游戏 [关键词]` | 查看收录的游戏 |

问法示例：

- `换位象棋怎么结算？`
- `十七步的番数怎么算`
- `情书有哪些成就，达成条件是什么`
- `狼人杀的选项倍率在哪里配`

每条 AI 回答末尾会自动附上免责声明（面板 `disclaimer` 可改，留空则不加）：

```
> 此条消息由智能助手检索源码生成，可能有误或遗漏，请以游戏内实际结算为准
```

以 `>` 开头，markdown 下渲染成引用块。只加在**模型生成的答案**后面 —— 帮助文案、
限流话术、报错提示都不加，那些是插件自己的确定性输出，挂「仅供参考」反而误导。
声明在答案入库**之后**才拼接，所以上下文库里存的是干净答案，不会随历史回灌给模型。

群聊回复的 `@提问人` 与正文之间隔**两个**换行，不是一个 —— markdown 里单换行只是
软换行、渲染出来就是个空格，`@` 和正文照样挤在同一行；两个换行才是段落分隔，
正文开头的引用块、列表、标题才能被当成块级元素解析。免责声明与正文之间同样用 `

`。

实际发出的消息长这样：

```
<@用户>
（空行）
十七步按番数结算，出处：mygame.cc:88
（空行）
> 此条消息由智能助手检索源码生成，可能有误或遗漏，请以游戏内实际结算为准
```

### 报错时附上具体原因

失败时除了固定话术，还会带上真实原因，省得只能去翻日志：

```
查询失败了，稍后再试一次；如果一直失败请联系管理员。
> 原因：两次作答均不合格: 问题需要源码依据却一个工具都没调用，就给出了 234 字的回答
```

原因是插件自己生成的确定性文本（接地闸的判定语、超长提示等），**不经模型，
所以不走内容审核** —— 审核针对的是模型产出。但仍会过一遍 IP 脱敏、压成单行
（避免破坏引用块）并按 `error_detail_chars` 截断：异常有可能包着接口返回的原始报文，
里面可能带内网地址或一长串 JSON，不适合原样丢给群友。

不想把内部判定暴露给群友就关掉面板的 `error_detail_enabled`。

## 它怎么工作

模型拿到五个**只读**工具，自己决定查几轮（默认最多 10 轮）：

| 工具 | 作用 |
|---|---|
| `list_games` | 列出全部游戏，中文名 ↔ 目录名对照 |
| `read_game_source` | **一次读全**某游戏的所有源码（机制类问题首选） |
| `read_game_rule` | 只读 `rule.md` + 真实文件清单（纯规则问题够用，更省） |
| `search_code` | 子串搜索，定位计分/结算/成就的实现位置 |
| `read_file` | 按行窗口读文件，返回带行号内容 |
| `list_dir` | 列目录，确认有哪些文件可读 |

### 为什么要「整包读取」

游戏目录的文件数差异很大（实测 3~13 个），**机制往往实现在额外的 `.h` 里**，
不只是 `mygame.cc`。让模型自己猜该读哪个，既多绕几轮也容易漏。加上中央模块的
XML 回退协议本身不稳，每多一轮工具调用就多一次失败机会 —— 一次读全能把轮数压到最少。

### ⚠️ 输入字符预算（接口硬上限）

接口对**单次输入总字符**有硬上限，超了直接 `HTTP 413`、整轮报废，**重试也没用**
（实测某接口 deepseek / qwen3 系 40000，jiutian 只有 9000）。

`input_budget_chars` 就是对标这个上限的总输入额度（默认 34000，按 40000 留 15% 余量）。
留给工具结果的额度由 `_tool_budget()` **每轮实测扣减**：

```
工具额度 = input_budget_chars − 系统提示词 − 工具 schema − 历史 − 问题 − 协议预留
```

实测固定开销约 9000 字符（光 tools schema 就 2719）。写死估值不靠谱 —— 历史长了照样 413，
所以动态算：无历史时额度 27888，满历史时收紧到 20804，**总输入恒定锁在 34000**。

工具结果按累计额度裁剪，超出部分截断并附明确说明（「不代表源码里只有这些」），
否则模型会把截断当成「代码里就这些」而下错结论。截断时按真实序列化长度收紧，
避免 JSON 转义（换行 `
`、引号 `\"` 各占两字符）导致越界。

> **换用上限更小的模型务必同步调小 `input_budget_chars`**，否则必然 413。
> 面板统计里的「超长失败」计数就是给这个用的。

实测 68 个游戏按**字符**计：中位 24840，最大 328102。默认额度下约半数能整包读全，
其余走降级。装不下时分三步降级：

1. 按优先级装整文件 —— `rule.md` / `achievements.h` / `options.h` 永远优先，
   其次主逻辑，再按 `focus` 关键词命中数排
2. 给了 `focus` 时预留三成预算，把**装不下但命中最多**的文件摘成片段
   （命中行 ±15 行，重叠合并，**保留原文行号**）—— 命中最多的文件往往也最大，
   一字不给等于把答案丢了
3. `files_omitted` 如实列出没读到的文件与命中数，并要求模型用
   `search_code` / `read_file` 补齐，不得因为没读到就当作不存在

`files_included` / `files_excerpted` 都会计入「模型真实看到过的路径」，
所以引用片段里的行号不会被接地闸误判成捏造。

### 无工具合成兜底（应对 XML 协议失灵）

审计日志显示的真实故障链：模型在 XML 协议下**连续两轮正常调用工具**（`ok=True`），
第三轮却照抄自己前两轮被写成 `[请求执行工具]` 的 assistant 内容，占位符就成了答案。
**带工具重试会踩同一个坑**（实测重试轮 `tools=0` 直接吐占位符）。

关键立足点：`_text_tool_protocol(tools)` 在 **tools 为空时返回空串**
（`modules/ai_llm/app/service.py:1793`），而 `[请求执行工具]` 只在 `text_protocol`
分支里产生。所以兜底这一轮把工具**彻底拿掉**：

| 情况 | 补救方式 |
|---|---|
| **调用过内容工具**，只是最后一步没写出答案 | **无工具合成**：把 transcript 塞进消息，`tools=None` 再调一次 |
| 没读到任何源码（只列了清单、或工具那步就崩了） | 带纠正指令重来一轮，**仍带工具**去查 |

判据是「调用过 `_CONTENT_TOOLS`」而**不是**「transcript 非空」—— `list_games` / `list_dir`
只给目录清单，拿它去合成只会得出「没有查到」。实测踩过：模型只调了 `list_games` 就作答，
被接地闸拦下后却拿这份清单去合成，于是回了「没有查到关于…的规则」，而代码其实就在那儿。

合成这一轮不存在 XML 协议、没有工具可调，模型只能基于已有结果写答案，
占位符从机制上无从产生。走独立 `consumer_plugin='lgtbot_qa_synth'` 便于审计区分，
面板统计有「合成兜底」计数。

### 内部占位符防护

中央模块在 XML 回退协议下，用 `[请求执行工具]` 占住「模型只发工具调用、没有正文」
的那一轮（`modules/ai_llm/app/service.py:1888`）。模型在后续轮次看到自己「说过」这句，
会照抄成最终答案 —— 实测发生过，用户收到的整条回复就是那七个字。

`_placeholder_answer()` 拦掉「整条答案只是一个方括号标记」的情况。这类回答长度极短、
没有假出处、也没有 XML 标签，三道接地闸全部放行，必须单独拦。

系统提示词强制要求：**先检索再回答，不许凭记忆编造**；结算类问题必须读 `mygame.cc`
的真实实现，`rule.md` 与代码冲突时以代码为准并指出不一致；结论要附 `文件:行号` 出处。

### 内容安全审核

与 **AI 聊天陪伴** 同口径（`DEFAULT_SAFETY_REVIEW_PROMPT` 逐字一致，用例里做了断言）。
本插件尤其需要出口把关：回答素材来自玩家通过 LGTBot_deploy 上传的游戏源码，
`rule.md` / `*.cc` 里可能夹带任何东西，模型转述出来就等于机器人自己说的。

三层，从确定性到概率性：

| 层 | 作用 | 失灵风险 |
|---|---|---|
| 违规词黑名单 | 命中即整条替换为安全回复 | 无（纯字符串匹配） |
| IP 脱敏 | 正则粗筛 + `ipaddress` 确认，真 IP 换成 `[IP已隐藏]` | 无（版本号不误伤） |
| 模型复审 | 独立一次调用分类输入与输出 | 会误判、也可能不可用 |

**输出审核永远 fail-closed**：审核不可用（模型乱答、超时、报错）一律不发，
不受 `moderation_fail_closed` 影响 —— 那个开关只管**输入**。
审核模型只允许返回「安全」或「内容违规，已禁止发送」，返回别的一律当不可用，
免得模型胡乱回一句就被当成放行。

被拦下时回的是插件固定话术，**不挂免责声明**（那不是 AI 的回答），
并且连同这一轮的提问一起从上下文库撤回 —— 违规文本不入库，
否则下一轮会当历史回灌给模型，把污染留在会话里。

审核走独立的 `consumer_plugin='lgtbot_qa_review'`，中央审计里能和问答调用分开看。
面板统计有「拦下的输入 / 拦下的输出」两个计数。

> 桌游规则天然含「杀」「攻击」「血量」这类词，可能被判违规。宁可误伤也不放行是刻意
> 取舍；确有需要就在面板调审核提示词，**不要整条关掉**。

### 接地闸：不许没读代码就作答

实测模型会**整段编造** —— 引用 `<游戏>/game_logic/combinations.py:212-230` 这种路径写出
上千字机制说明，而整个项目是 C++、连一个 `.py` 都没有。光在提示词里写「要先检索」拦不住，
所以加了三道程序化闸门，全部与具体游戏无关：

| 闸 | 触发条件 | 依据 |
|---|---|---|
| 捏造出处 | 答案里的 `文件:行号` 指向工具没返回过、沙箱里也不存在的文件 | 铁证 |
| 零检索 | 一个工具都没调用，却超出该问题类型的字数上限 | 纯凭想象 |
| 只列不读 | 只调了 `list_*`、没读任何文件，却写出 > 300 字机制说明 | 同上 |

两道长度闸都要看**问题类型**，判据还不一样 —— 一刀切必然误杀：

| 闸 | 判据 | 为什么 |
|---|---|---|
| 零检索 | `_needs_source`：点名真实游戏 **或** 带机制词 | 什么都没查就作答，风险最高，从严 |
| 只列不读 | `_mentions_game`：点名了真实游戏 | `list_games` 连简介一起返回，浏览/推荐问题据此作答完全站得住 |

两次生产事故都是一刀切造成的：

- 「LGTBot 是什么」被统一的 60 字死线连挂两次（163 字、104 字），而那问题根本没源码可读
- 「推荐几款休闲非竞技的多人游戏」，模型用 `list_games` 给出了一段 466 字的正确推荐，
  被「只列不读」闸误杀 → 重试时被纠正指令带偏，反过来叫**用户**自己去运行 `list_games`，
  那条错的短回复只有 52 字、顺利过闸发了出去

后一条的教训很直接：**闸误杀正确答案后，重试产出的往往比原答案更差**，因为纠正指令
把模型推向了错误方向。所以宁可放宽判据，也不要让正确答案进重试。

零检索闸的分档：

| 问题类型 | 判据 | 零检索上限 |
|---|---|---|
| 需要源码 | 点名了索引里真实存在的游戏，**或**带机制类词汇（结算/计分/成就/触发…） | 60 字 |
| 元问题 | 两者都不沾（「LGTBot 是什么」「谁开发的」） | 500 字 |
| 判断不了 | 问题为空 | 从严（60 字） |

两道闸的「判断不了」都 fail-safe 到从严 —— 宽松通道只发给能确认无需源码的提问。

另外提示词里明确了**工具由模型自己调用**：实测出现过回复「请先运行 `list_games`」
这种把工具当成用户命令的错误。

游戏名比对是**数据驱动**的（拿真实索引比对中文名与目录名，不写死任何游戏）；
机制词是通用领域词而非游戏名 —— 加它是因为问一个**不存在的游戏**「怎么结算」时，
光比对索引会判成元问题，等于放任模型对着虚构游戏编 500 字。

元问题能答对，靠的是 `app/central.py` 的 `PROJECT_FACTS`：把 LGTBot 的权威事实
（C++20 多人文字推理游戏裁判库、50+ 游戏、作者 @Slontia、「LGT」出自《Liar Game》、
本插件是 ElainaBot_v2 适配层）预置进提示词，逐条对应上游 README 的「致谢与项目来源」。
不预置的话模型只会拿它对这个小众项目的先验作答，而那个先验基本是错的。

命中任一闸 → 附纠正指令重新生成一次；**两次都不合格就报错，绝不把没有依据的答案发出去**。
编造的规则比「查询失败」危害大得多。

长度分档是为了不误伤：「没有查到」「你问的是哪个版本？」不需要检索；
「已收录 67 个游戏，包括……」只靠 `list_games` 就能答且可能较长。
出处按 basename 比对，所以模型把完整路径缩写成 `mygame.cc:88` 不会被误判。

配套的两条硬约束写死在 `app/central.py`（不进面板可编辑的 `system_prompt`，
避免被改写或被旧配置覆盖）：

- `CODE_LAYOUT_RULE` —— 声明这是 C++ 项目、没有 Python、列出每个游戏的常见文件，
  并**禁止臆造任何目录名、文件名或行号**
- `GROUNDING_RULE` —— 涉及规则/数值/判定/结算的问题必须先真正读到内容，
  读不到就只能回答「没有查到」；同时要求回答简短，不写分点长文与「举例说明」式枚举
  （那种结构最容易掺进臆测）

另外 `read_game_rule` 现在连同该游戏**真实存在的文件清单** `source_files` 一起返回 ——
把真实清单摆在眼前，编路径就失去了空间。

### 两跳查找：名词在定义处，实现在标识符里

源码里机制常常分两层：用户说的名词（技能名、状态名、术语）往往只出现在**定义处**，
而「怎么排序、何时触发、按什么条件判定」的真正实现，在它调用或重写的函数名、
枚举、常量里 —— 那些地方通常一个中文名词都不出现。

实战教训：问某天赋在选牌阶段的排序，中文名只出现在天赋类的定义里（4 处），
而真正的排序与并列判定在主逻辑的 `std::sort` 里，那段代码**一个中文名词都没有**，
只出现定义里那个虚函数名。只按中文词检索必然得出「没有查到」。

所以 `GROUNDING_RULE` 明确要求：读到定义后，若问题问的是顺序 / 时机 / 计算方式，
**把定义里出现的函数名或标识符当作新关键词再 `search_code` 一次**，定位到真正的实现再作答；
用中文词搜不到不等于不存在，换成代码里的英文标识符再搜。停在定义上就会误判成「没有这个机制」。

工具侧本就支持这条链路：`read_game_source` 的片段是命中行 ±15 行，
足以把定义体里的虚函数名一起带出来，模型据此就能发起第二跳。

### 对模型常见失误的容错

模型调用工具时会犯几类固定错误，工具层直接兼容掉，而不是报错让它自己猜：

| 模型写法 | 处理 |
|---|---|
| `scope="天赋云巢"`（中文游戏名当路径） | 按游戏名解析到该游戏目录 |
| `file_pattern=".cc"`（缺通配符） | 补成 `*.cc`；`"cc"` 补成 `*cc*` |
| 窄范围搜空 | 顺带告诉它这个词出现在哪些游戏里 |

最后一条是实战教训：问「天赋云巢的癞子会触发组合龙吗」，模型把范围锁在
`talent_comb` 搜「组合龙」得 0 条，就要下「没有这个机制」的结论了 —— 实际上组合龙
在 `talent_comb_beta`（天赋云巢beta）里。现在搜空会返回 `found_in_other_games`，
模型据此改搜正确的游戏。全库都没有时则明确要求「如实告知，不要臆测」。

### 工具调用 XML 泄漏防护

中央模块在模型不输出原生 `tool_calls` 时会退回 XML 文本协议，但它的解析器只认
`<工具名><参数名>值</参数名></工具名>`（`modules/ai_llm/app/service.py:114`）。模型很容易
写成属性式 `<工具名 参数="值"/>` —— 那样**一个都匹配不上**，raw XML 会原样变成答案发给
用户，中央层还记为 `success`，用户看到一堆标签且没有下文。

两道防护：

1. `app/central.py` 的 `TOOL_FORMAT_RULE` 把正确格式写死进 system prompt。刻意不放在
   面板可编辑的 `system_prompt` 里 —— 那个会被用户改写或被旧配置覆盖，而这是正确性硬约束。
2. `main.py` 的 `_leaked_tool_xml()` 检测答案里残留的工具标签，命中则附纠正指令重试一次；
   仍失败就走异常分支报错，**绝不把 raw XML 发给用户**。

中文名从 `mygame.cc` 的 `k_properties`（`.name_` / `.description_`）解析，逻辑与
`LGTBot_deploy/app/review.py` 保持一致（支持相邻字符串字面量拼接）。索引按
`mygame.cc` 的 mtime+size 缓存，玩家上传新游戏后自动失效重建。

## 零外部插件依赖

**生产环境可能没有装 AI 开发插件**，所以本插件的检索能力全部自带，不复用任何其他插件的工具：

| 模块 | 内容 |
|---|---|
| `app/sandbox.py` | 只读沙箱：路径校验、目录遍历、行窗口读取 |
| `app/tools.py` | 六个工具（`list_games` / `read_game_source` / `read_game_rule` / `search_code` / `read_file` / `list_dir`）全部本插件实现 |
| `app/games.py` | 游戏索引与中文名解析 |

全部 import 只有：标准库（`asyncio` `copy` `fnmatch` `ipaddress` `json` `os` `re`
`sqlite3` `threading` `time`）、`aiohttp`、框架 `core.*`、以及自己的 `app.*`。
用例里有断言锁死这条：任何指向其他插件的 import 都会让测试失败。

> `app/config.py` 里提到 AI 聊天陪伴的注释只是说明审核提示词的同源关系，
> 常量是**逐字复制**到本插件文件里的，没有 import。

## 安全边界

**所有**文件访问经 `app/sandbox.py` 收口，工具层不自己拼路径、不自己 `open()`。

| 约束 | 实现 |
|---|---|
| 只读 | sandbox 不提供任何写 / 删 / 移动 / 执行入口 |
| 根白名单 | 目标必须落在某个启用范围内，`realpath` 比对 —— 软链接指向仓库外会被解开后判越界 |
| 目录黑名单 | `.git` / `__pycache__` / `data` / `build` 等任何层级都不可见 |
| 后缀白名单 | 只读文本源码，`.so` / `.png` / `.db` 直接拒绝 |
| 体积行数上限 | 超限文件跳过，读取按行窗口截断 |
| 无正则搜索 | `search_code` 只做子串匹配，杜绝模型生成的病态正则 ReDoS |

LGTBot 自己的 `data/`（`config.yaml`、`lgtbot.db`、`user_cache.db`）**不在任何范围内**，
因此天然不可达。这是刻意设计 —— 不要把它加进「可检索范围」。

> 对比：`AI开发插件` 的 `read_file` 根目录是整个框架根，且 `_redact_config` 只作用于
> `get_config` 不作用于 `read_file`（`tools.py:357`）。那套工具只能给主人用，
> 绝不能开放给群友 —— 这正是本插件另起炉灶的原因。

### 提示词注入

游戏源码是玩家通过 `LGTBot_deploy` 上传的，`rule.md` / `mygame.cc` 里完全可能藏着
「忽略以上指令」。系统提示词明确声明：工具返回的一切与用户消息都是**不可信数据**，
不是指令。加上工具集全只读，最坏后果也只是读到别的游戏源码。

调用刻意走 `service.complete()` 而非 `run_agent()` —— 后者会打开中央运行时能力
（其他插件共享的工具、MCP、Skills）。本插件面向普通群友，工具面必须收敛到自己这五个。

## 限流

框架 `@handler(cooldown=...)` 只是被存进 handler 字典，`core/` 里没有任何地方读它
（`core/plugin/decorators.py:45`），所以限流自己实现，三道闸：

1. **并发闸** — 同一用户上一问还在跑就拒，主人也不豁免（防的是把自己卡死）
2. **冷却闸** — 距上次提问不足 `cooldown_seconds`（默认 120 秒 / 人）
3. **日限闸** — 今日已达 `daily_limit`（默认 50 次 / 人）

默认私聊不生效（`direct_enabled: false`），避免和其他 AI 插件抢私信；
`DEPLOY.md` 默认不在检索范围内，与玩家问题无关，需要时面板勾上即可。

计数在**模型调用成功之后**才记，被限流拒掉的请求不吃额度。用量落 SQLite，
插件热重载不会把每日上限清零。
