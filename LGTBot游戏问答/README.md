# LGTBot 游戏问答

@机器人提问 LGTBot 桌游的规则、玩法、计分与结算，AI 现场检索 LGTBot 源码后带出处作答。

与 **AI 聊天陪伴**、**AI 开发助手** 完全独立：自己的配置、自己的上下文库、自己的限流，
共用的只有 `modules/ai_llm` 这一个模型底座。

---

## ⚠️ 部署前必读：必须做 bot 绑定

默认触发方式 `at` 注册的是 `.*` + `block=True` 的兜底 handler。而 LGTBot 把玩家的
**所有游戏输入**靠 `priority=-100` 的「LGTBot 消息派发」兜底送进 C++ 引擎
（`plugins/LGTBot_ElainaBot/mod/dispatcher.py`）。

`block` 在**匹配阶段**就 `break`（`core/plugin/_dispatch.py:269`），handler 函数体根本
来不及执行。所以两个插件跑在同一个 bot 上时，本插件会把游戏派发整条掐断，**所有对局失联**。

框架的 bot 白名单检查在 block 判定**之前**（`core/plugin/_dispatch.py:231`），因此：

> 到「插件管理 → bot 绑定」，把 **LGTBot游戏问答** 绑到问答 bot、
> **LGTBot_ElainaBot** 绑到游戏 bot。两者互不可见，block 就伤不到 LGTBot。

未绑定且检测到 LGTBot 也加载时，插件加载会打 WARNING，面板顶部显示红色横幅。
不想绑定就把触发方式改成 `prefix`（只有 `/问 xxx` 才命中并拦截）。

### ⚠️ 全量群（non_at_message）另有一坑

框架那道「非 @ 消息过滤」的真实条件是：

```python
if is_non_at and not h.get('ignore_at_check', False) and not non_at_ok:
    continue          # core/plugin/_dispatch.py:238
```

**不设 `ignore_at_check` 不等于「只吃 @ 消息」** —— 全量群下 `non_at_ok` 为真，
这条 `continue` 不执行，`at` 模式的 `.*` 兜底会匹配群里**每一条**消息。

所以 `at_message` 函数体里自己再判一次（`_at_ok`，与 LGTBot 的消息派发同一套判据）。
**关键是只对 `GROUP_MESSAGE_CREATE` 卡 `is_at_self`**，不能对所有群消息都卡：

| 事件 | `is_at_self` | 放行 | 为什么 |
|---|---|---|---|
| `GROUP_AT_MESSAGE_CREATE` | 任意 | ✅ | 事件类型本身就代表 @ 了 bot |
| `GROUP_MESSAGE_CREATE` | `False` | ❌ | 全量群的日常聊天 |
| `GROUP_MESSAGE_CREATE` | `True` | ✅ | 全量群里冲着 bot 来的 |
| 私聊 / 频道私信 | — | ✅ | 没有「@」概念 |

`is_at_self` 是从 payload 的 `mentions` 数组推出来的，而 QQ 官方 bot 的
**AT_CREATE payload 不一定带 mentions**（AT 信号在事件类型里，不在 payload 里重复）。
对它硬卡 `is_at_self` 会把非全量群的正常提问**全部误挡** —— 这个坑踩过一次。
框架自己也是这个约定：

```python
# 仅全量群消息区分是否艾特机器人; 非全量消息收不到未艾特消息, 一律算艾特
at_bot = event.is_at_self if event.event_type == GROUP_MESSAGE_CREATE else True
#                                                    core/bot/event.py:178
```

但 `block` 是在**匹配阶段**生效的，函数体 `return` 收不回来：那些非 @ 消息
虽然不会被回复，却已经对更低优先级的插件不可见了。所以：

> 同 bot 上还有别的插件要处理非 @ 消息时，把面板的**「拦截后续插件」关掉**
> （`block_others: false`）。真的在全量群吃到非 @ 消息时，日志每 10 分钟会告警一次。

## 安装

1. 放进 `plugins/`，框架自动加载。
2. 启用 `modules/ai_llm`（AI LLM 服务），在其面板配好接口、Key 和模型。
   本插件**不保存任何密钥**。
3. 做上面的 bot 绑定。
4. 打开侧边栏「LGTBot 问答」页，确认「可检索范围」全部就绪。

源码目录默认自动定位同框架的 `plugins/LGTBot_ElainaBot`。`lgtbot/` 是 git submodule，
没拉取时面板会报红，服务器上执行：

```bash
git submodule update --init --recursive lgtbot
```

## 使用

| 指令 | 说明 |
|---|---|
| `@机器人 <问题>` | 直接提问（`at` / `both` 模式） |
| `/问 <问题>` | 前缀提问（`prefix` / `both` 模式） |
| `/问答` | 查看用法 |
| `/问答 清空` | 清空自己的追问上下文 |
| `/问答 游戏 [关键词]` | 查看收录的游戏 |

问法示例：

- `换位象棋怎么结算？`
- `十七步的番数怎么算`
- `情书有哪些成就，达成条件是什么`
- `狼人杀的选项倍率在哪里配`

开了画图之后还能 `画一张下雪的山间小屋` —— 只在明确要求画图时才会出图，
规则问题照常检索源码作答，不会给你配图。要画的东西属于某个游戏时（`画一张某某的棋盘`），
会**先去读该游戏源码**、拿到真实描述再画，而不是照着游戏名瞎想。

每条 AI 回答末尾会自动附上免责声明（面板 `disclaimer` 可改，留空则不加）：

```
> 此条消息由智能助手检索源码生成，可能有误或遗漏，请以游戏内实际结算为准
```

以 `>` 开头，markdown 下渲染成引用块。只加在**模型生成的答案**后面 —— 帮助文案、
限流话术、报错提示都不加，那些是插件自己的确定性输出，挂「仅供参考」反而误导。
声明在答案入库**之后**才拼接，所以上下文库里存的是干净答案，不会随历史回灌给模型。

群聊回复的 `@提问人` 与正文之间隔**两个**换行，不是一个 —— markdown 里单换行只是
软换行、渲染出来就是个空格，`@` 和正文照样挤在同一行；两个换行才是段落分隔，
正文开头的引用块、列表、标题才能被当成块级元素解析。免责声明与正文之间同样用 `

`。

实际发出的消息长这样：

```
<@用户>
（空行）
十七步按番数结算，出处：mygame.cc:88
（空行）
> 此条消息由智能助手检索源码生成，可能有误或遗漏，请以游戏内实际结算为准
```

### 报错时附上具体原因

失败时除了固定话术，还会带上真实原因，省得只能去翻日志：

```
查询失败了，稍后再试一次；如果一直失败请联系管理员。
> 原因：两次作答均不合格: 问题需要源码依据却一个工具都没调用，就给出了 234 字的回答
```

原因是插件自己生成的确定性文本（接地闸的判定语、超长提示等），**不经模型，
所以不走内容审核** —— 审核针对的是模型产出。但仍会过一遍 IP 脱敏、压成单行
（避免破坏引用块）并按 `error_detail_chars` 截断：异常有可能包着接口返回的原始报文，
里面可能带内网地址或一长串 JSON，不适合原样丢给群友。

不想把内部判定暴露给群友就关掉面板的 `error_detail_enabled`。

## 它怎么工作

模型拿到六个**只读**工具，自己决定查几轮（默认最多 10 轮）：

| 工具 | 作用 |
|---|---|
| `list_games` | 列出全部游戏，中文名 ↔ 目录名对照 |
| `read_game_source` | **一次读全**某游戏的所有源码（机制类问题首选） |
| `read_game_rule` | 只读 `rule.md` + 真实文件清单（纯规则问题够用，更省） |
| `search_code` | 子串搜索，定位计分/结算/成就的实现位置 |
| `read_file` | 按行窗口读文件，返回带行号内容 |
| `list_dir` | 列目录，确认有哪些文件可读 |

另有一个**默认关闭**的 `draw_image`（见下节「画图能力」），它不是检索工具。

### 为什么要「整包读取」

游戏目录的文件数差异很大（实测 3~13 个），**机制往往实现在额外的 `.h` 里**，
不只是 `mygame.cc`。让模型自己猜该读哪个，既多绕几轮也容易漏。加上中央模块的
XML 回退协议本身不稳，每多一轮工具调用就多一次失败机会 —— 一次读全能把轮数压到最少。

### 画图能力（可选，默认关闭）

「**AI 画图**」插件把自己的出图能力注册成了中央 AI LLM 的共享工具
（`ai_draw:tool:draw`，AI画图 1.5.0+）。本插件把它包装成模型可见的第七个工具
`draw_image`，用户说「画一张 xxx」时模型可以直接调用。

**本插件不含任何生图代码**。出图、线路故障转移、**描述的内容审核**、留档、每日额度
全部发生在 AI 画图那边；这里只决定「要不要把这个工具交给模型」和「一次问答最多画几张」。

| 面板项 | 默认 | 说明 |
|---|---|---|
| 允许模型调用画图 | ❌ 关 | 每张图都烧 AI 画图的接口额度，得管理员显式打开 |
| （自动）投递方式 | — | 有图床走 Markdown 图片消息，否则富媒体，见下 |
| 单次问答最多画几张 | 1 | 不设闸的话模型能在 10 轮里连画十张，一个提问掏空日额度 |
| 单次画图超时（秒） | 120 | 出图比模型调用慢得多，不复用 `request_timeout_seconds` |
| 已画图片保留（秒） | 86400 | 被打断或重问时复用现成的图，不重画；见下 |

#### 能力键不自己拼

按中央模块文档的要求，`capability_key` 从 `list_capabilities()` 的返回值里取，
不写死字符串。自己拼有两个问题：对方改了 id 就静默失效；而且绕过了
「这个能力当前是否授权给我」的判断（`_capability_allowed`）。

面板会把四种失败分开说清楚 —— 它们在模型侧的表现完全一样（工具调用失败），
但管理员要做的事完全不同：

| 状态 | 该做什么 |
|---|---|
| 未检测到画图能力 | 装 / 升级 AI 画图（≥1.5.0） |
| 能力不在线 | AI 画图插件没加载，或它自己的「对外开放」开关是关的 |
| 能力被停用 | 到 AI LLM 面板启用它 |
| 未授权给本插件 | 设为「共享给所有插件」，或把 `lgtbot_qa` 加进 `allowed_consumers` |

#### 关掉时工具不出现在清单里

只在执行入口挡是不够的：schema 一直挂着的话，模型会反复尝试一个注定失败的工具、
白烧轮数，schema 本身还要占输入预算。所以 `tools.schema_for()` 按开关返回 6 个或 7 个。

反过来，**执行入口也必须挡**（`tools.run` → `drawing.run`）：模型把调用写成 XML 文本、
被「代为执行」那条路捡起来时，绕过的正是 schema。

#### ⚠️ 超时额度必须覆盖画图，否则必被自己打断

`request_timeout_seconds`（默认 90）管的是**整次 `complete()`**，中央模块把工具执行
时间也算在里面。检索工具都是本地磁盘 IO 可以忽略，**画图不行** —— 一张几十秒，
直接把额度吃光，然后我们自己的 `asyncio.wait_for` 取消整条调用链。

中央那边把 `CancelledError` 记成 `error='interrupted'`
（`modules/ai_llm/app/service.py:1893`），生产审计日志里就是这样三条连着：

```
consumer_plugin = lgtbot_qa      error = interrupted
duration_ms = 90013 / 90012 / 90014      ← 正好卡在超时值上
```

三条 = `retry_attempts` 三次全被自己的超时打断，一次都没轮到模型写答案。**重试还会
让模型再画一张**，同一个请求烧两次额度，用户仍然什么都没收到。

所以 `central.tool_time_budget()` 在画图开着时按最坏情况加额度：

```
有效超时 = request_timeout_seconds + draw_timeout_seconds × draw_max_per_question
```

加的是上界（默认 90 + 120×1 = 210 秒），只有真画图才会用到；画图关着时一秒不加。

#### 被打断也不重画

光加额度不够 —— 网络更慢、或管理员把超时调小，照样可能中途被取消。两层兜底：

| 机制 | 作用 |
|---|---|
| `asyncio.shield` + 独立任务 | 调用方被取消时，**画图任务继续跑完**并把结果落盘 |
| `draw_cache` 表（SQLite） | 重试 / 用户重问同样的描述时直接复用，不重新生成 |

缓存键是 `sha1(scope + prompt)` —— **带上 scope 是刻意的**：不同用户提同样的描述
各自出各自的图，只有同一个人重试或重问才复用，那正是被打断后要救的场景。

复用**不占**单次问答的张数上限（`drawing.reusable()`）。少了这一步，被打断后的重试
会卡在「本次已经画过 1 张」上 —— 明明有现成的图，却一张都发不出去。

`_pending` 还顺手解决了并发同描述：同一个人的两次请求撞上同一张图时只画一次，
两边都等那个任务。发送前按 URL 去重，同一张图不会连发两条。

#### ⚠️ 画游戏里的东西，必须先读到源码

**这是一道程序闸，不是提示词请求。** 用户说「画一张某某游戏的棋盘 / 角色」时，
模型若直接调画图，只能按游戏名脑补 —— 画出来跟游戏毫无关系，而用户要的恰恰是
「**这个游戏里的**东西」。

所以 `_draw_needs_source()` 在工具入口拦一道：

| 条件 | 处理 |
|---|---|
| 这次请求点到了索引里**真实存在**的游戏，且还没调用过内容工具 | 拒绝，并要求先 `read_game_source` / `read_game_rule` |
| 已经读过源码 | 放行 |
| 没点到任何游戏（画只猫、画个风景） | 放行，不平白多绕一轮 |

判据与接地闸同源：拿真实游戏索引比对，**不写死任何游戏名**。
连模型自己填的 `prompt` 一起看 —— 追问式的「画一张这个游戏的插画」问题里没有游戏名，
但模型展开后的描述里通常有。

被拒这一次**不计入画图张数上限**（它没画）。返回给模型的是可执行的下一步指令而不是
一句「不行」—— 只说不行，模型往往就放弃画图改写一段文字解释了。

#### 图片链接不给模型看

`drawing.detach_image()` 在结果回灌前就把 `url` / `size` 摘掉，模型只收到一句
「图片已生成，机器人会自动发给用户」。模型拿到链接就会往答案里贴，而 QQ 那边裸链接
会被风控、Markdown 图片语法在普通文本消息里也渲染不出来，用户只能看到一串 URL。

#### 投递：图床优先 Markdown，否则富媒体

图片**单独发一条**消息，不塞进答案正文：富媒体消息不渲染引用块，Markdown 消息里
塞长正文也会把免责声明的格式弄乱。顺序是文字在前、图片在后。

| 条件 | 发送方式 |
|---|---|
| Image Hosting 有可用图床 | Markdown 图片消息：`<@发起人>` 换行 `![alt #宽px #高px](链接)` |
| 没有图床，或 Markdown 没送达 | 富媒体图片消息（`reply_image`） |

优先 Markdown 是因为**富媒体消息不解析 `<@openid>`** —— 群里多人同时提问时，
收到一张没头没尾的图根本对不上是谁问的。

`#宽px #高px` 用 AI 画图返回的 **`width` / `height`（它自己解析图片头拿到的实测像素）**，
不是 `requested_size`：有些线路并不严格按请求尺寸出图，照请求值写会让客户端按错误的
比例给图占位。它下不到图片字节时**不返回**这两个键（免得 0 被当成真实值），那才退回
`requested_size`，再不行按 1024 见方 —— 这两个数只是排版提示，不该为它拦下一张画好的图。

> 字段在 AI 画图 1.5.1 变过：原来的 `size` 改名 `requested_size`，实测值另开
> `width` / `height`。`drawing._dimensions()` 两个键名都认，对方版本没跟上也取得到数。

> **本插件不自己上传图床。** 图是 AI 画图生成的，它在返回链接前已经用**同一个**
> `image_hosting` 模块传过一次（`AI画图/app/capability.py`）。这边再下载回来传一遍
> 纯属重复，还多一次失败机会 —— 所以 `app/hosting.py` 只判断可用性。

Markdown 失败的典型原因是**图床域名没在 QQ 开放平台报备**，或上游那次上传没成功、
回来的其实是接口原始链接。两种都靠退回富媒体救回来，不需要猜链接的来历。

投递放在 `finally` 里：图一旦画出来，对方的额度就已经扣了，后面哪一步失败
（作答不合格、审核报错、发文字失败）都不该让这张图作废。**唯一不发的情况**是
输出内容审核明确拦下了这一轮 —— 那时整轮判定为不该发出去，单发一张图自相矛盾。

平台失败时框架**不一定抛异常**，也可能只返回 `None` 或不带消息 ID 的响应体，
所以要看返回值判送达。光看异常不仅会把失败记成成功，还会让「退回富媒体」根本不触发
（面板「累计出图」只计真正送达的）。

#### 接地闸让路

画图成功时闸 2、闸 3 全部放行。不放行的话，「画一张某某游戏的插画」会同时踩中
「点名了具体游戏」和「没调用内容工具」，被判臆造毙掉，**重试还会再画一张** ——
白烧一次额度还多发一条图。闸 1（编造出处）任何时候都不放过。

#### 这不等于打开了中央运行时

接的是**一个**点名的能力，不是 `runtime_capabilities=['tool']`。后者会把所有插件
共享的工具、MCP、Skills 整片放进来，那是面向群友的问答机器人不该有的工具面。

### ⚠️ 输入字符预算（接口硬上限）

接口对**单次输入总字符**有硬上限，超了直接 `HTTP 413`、整轮报废，**重试也没用**
（实测某接口 deepseek / qwen3 系 40000，jiutian 只有 9000）。

`input_budget_chars` 就是对标这个上限的总输入额度（默认 34000，按 40000 留 15% 余量）。
留给工具结果的额度由 `_tool_budget()` **每轮实测扣减**：

```
工具额度 = input_budget_chars − 系统提示词 − 工具 schema − 历史 − 问题 − 协议预留
```

实测固定开销约 9000 字符（光 tools schema 就 2719）。写死估值不靠谱 —— 历史长了照样 413，
所以动态算：无历史时额度 27888，满历史时收紧到 20804，**总输入恒定锁在 34000**。

工具结果按累计额度裁剪，超出部分截断并附明确说明（「不代表源码里只有这些」），
否则模型会把截断当成「代码里就这些」而下错结论。截断时按真实序列化长度收紧，
避免 JSON 转义（换行 `
`、引号 `\"` 各占两字符）导致越界。

> **换用上限更小的模型务必同步调小 `input_budget_chars`**，否则必然 413。
> 面板统计里的「超长失败」计数就是给这个用的。

实测 68 个游戏按**字符**计：中位 24840，最大 328102。默认额度下约半数能整包读全，
其余走降级。装不下时分三步降级：

1. 按优先级装整文件 —— `rule.md` / `achievements.h` / `options.h` 永远优先，
   其次主逻辑，再按 `focus` 关键词命中数排
2. 给了 `focus` 时预留三成预算，把**装不下但命中最多**的文件摘成片段
   （命中行 ±15 行，重叠合并，**保留原文行号**）—— 命中最多的文件往往也最大，
   一字不给等于把答案丢了
3. `files_omitted` 如实列出没读到的文件与命中数，并要求模型用
   `search_code` / `read_file` 补齐，不得因为没读到就当作不存在

`files_included` / `files_excerpted` 都会计入「模型真实看到过的路径」，
所以引用片段里的行号不会被接地闸误判成捏造。

### 瞬时故障重试与断点续答

一次问答常常已经跑了十几个工具（读规则、整包读源码、顺着标识符追一跳…），
中途一次 `524` 或「接口返回了空消息」就把这些全丢掉太亏 —— 用户还白等了几十秒。
两层保护：

**一、瞬时故障自动重试**（`central._bounded`，线性退避 `delay × 第几次`）

| 类别 | 例子 | 处理 |
|---|---|---|
| 瞬时 | `524` `502` `503` `429` `500`、网关超时、连接重置、**接口返回了空消息** | 重试（默认 3 次） |
| 永久 | `413` 超长、`context_length_exceeded`、`401/403` 鉴权、没有可用接口 | **不重试**，直接上抛 |

永久类判定放在瞬时判定**之前** —— 否则 `413` 里的数字、鉴权报文里的词会被误判成瞬时，
白白重试三次烧掉时间和额度。

> `make_coro` 必须是**每次现造协程的工厂**：协程不能 `await` 两次，
> 传现成的协程对象重试时会直接 `RuntimeError`。

**二、断点续答**（`main._resumable`）

重试用尽仍失败时，只要**已经读到过源码**，就不报错而是改用无工具合成：把 `transcript`
交给模型直接写答案。这一轮不带工具、上下文也小得多，成功率明显更高，检索成果也保住了。

只有两种情况才真的上抛：一次源码都没读到（没东西可续），或错误是 `413` 这类
**续了照样失败**的硬错误。面板统计有「断点续答」计数。

### 无工具合成兜底（应对 XML 协议失灵）

审计日志显示的真实故障链：模型在 XML 协议下**连续两轮正常调用工具**（`ok=True`），
第三轮却照抄自己前两轮被写成 `[请求执行工具]` 的 assistant 内容，占位符就成了答案。
**带工具重试会踩同一个坑**（实测重试轮 `tools=0` 直接吐占位符）。

关键立足点：`_text_tool_protocol(tools)` 在 **tools 为空时返回空串**
（`modules/ai_llm/app/service.py:1793`），而 `[请求执行工具]` 只在 `text_protocol`
分支里产生。所以兜底这一轮把工具**彻底拿掉**：

| 情况 | 补救方式 |
|---|---|
| **调用过内容工具**，只是最后一步没写出答案 | **无工具合成**：把 transcript 塞进消息，`tools=None` 再调一次 |
| 没读到任何源码（只列了清单、或工具那步就崩了） | 带纠正指令重来一轮，**仍带工具**去查 |

判据是「调用过 `_CONTENT_TOOLS`」而**不是**「transcript 非空」—— `list_games` / `list_dir`
只给目录清单，拿它去合成只会得出「没有查到」。实测踩过：模型只调了 `list_games` 就作答，
被接地闸拦下后却拿这份清单去合成，于是回了「没有查到关于…的规则」，而代码其实就在那儿。

合成这一轮不存在 XML 协议、没有工具可调，模型只能基于已有结果写答案，
占位符从机制上无从产生。走独立 `consumer_plugin='lgtbot_qa_synth'` 便于审计区分，
面板统计有「合成兜底」计数。

### 内部占位符防护

中央模块在 XML 回退协议下，用 `[请求执行工具]` 占住「模型只发工具调用、没有正文」
的那一轮（`modules/ai_llm/app/service.py:1888`）。模型在后续轮次看到自己「说过」这句，
会照抄成最终答案 —— 实测发生过，用户收到的整条回复就是那七个字。

`_placeholder_answer()` 拦掉「整条答案只是一个方括号标记」的情况。这类回答长度极短、
没有假出处、也没有 XML 标签，三道接地闸全部放行，必须单独拦。

系统提示词强制要求：**先检索再回答，不许凭记忆编造**；结算类问题必须读 `mygame.cc`
的真实实现，`rule.md` 与代码冲突时以代码为准并指出不一致；结论要附 `文件:行号` 出处。

### 内容安全审核

与 **AI 聊天陪伴** 同口径（`DEFAULT_SAFETY_REVIEW_PROMPT` 逐字一致，用例里做了断言）。
本插件尤其需要出口把关：回答素材来自玩家通过 LGTBot_deploy 上传的游戏源码，
`rule.md` / `*.cc` 里可能夹带任何东西，模型转述出来就等于机器人自己说的。

三层，从确定性到概率性：

| 层 | 作用 | 失灵风险 |
|---|---|---|
| 违规词黑名单 | 命中即整条替换为安全回复 | 无（纯字符串匹配） |
| IP 脱敏 | 正则粗筛 + `ipaddress` 确认，真 IP 换成 `[IP已隐藏]` | 无（版本号不误伤） |
| 模型复审 | 独立一次调用分类输入与输出 | 会误判、也可能不可用 |

**输出审核永远 fail-closed**：审核不可用（模型乱答、超时、报错）一律不发，
不受 `moderation_fail_closed` 影响 —— 那个开关只管**输入**。
审核模型只允许返回「安全」或「内容违规，已禁止发送」，返回别的一律当不可用，
免得模型胡乱回一句就被当成放行。

被拦下时回的是插件固定话术，**不挂免责声明**（那不是 AI 的回答），
并且连同这一轮的提问一起从上下文库撤回 —— 违规文本不入库，
否则下一轮会当历史回灌给模型，把污染留在会话里。

审核走独立的 `consumer_plugin='lgtbot_qa_review'`，中央审计里能和问答调用分开看。
面板统计有「拦下的输入 / 拦下的输出」两个计数。

> 桌游规则天然含「杀」「攻击」「血量」这类词，可能被判违规。宁可误伤也不放行是刻意
> 取舍；确有需要就在面板调审核提示词，**不要整条关掉**。

### 接地闸：不许没读代码就作答

实测模型会**整段编造** —— 引用 `<游戏>/game_logic/combinations.py:212-230` 这种路径写出
上千字机制说明，而整个项目是 C++、连一个 `.py` 都没有。光在提示词里写「要先检索」拦不住，
所以加了三道程序化闸门，全部与具体游戏无关：

| 闸 | 触发条件 | 依据 |
|---|---|---|
| 捏造出处 | 答案里的 `文件:行号` 指向工具没返回过、沙箱里也不存在的文件 | 铁证 |
| 零检索 | 一个工具都没调用，却超出该问题类型的字数上限 | 纯凭想象 |
| 只列不读 | 只调了 `list_*`、没读任何文件，却写出 > 300 字机制说明 | 同上 |

两道长度闸都要看**问题类型**，判据还不一样 —— 一刀切必然误杀：

| 闸 | 判据 | 为什么 |
|---|---|---|
| 零检索 | `_needs_source`：点名真实游戏 **或** 带机制词 | 什么都没查就作答，风险最高，从严 |
| 只列不读 | `_mentions_game`：点名了真实游戏 | `list_games` 连简介一起返回，浏览/推荐问题据此作答完全站得住 |

两次生产事故都是一刀切造成的：

- 「LGTBot 是什么」被统一的 60 字死线连挂两次（163 字、104 字），而那问题根本没源码可读
- 「推荐几款休闲非竞技的多人游戏」，模型用 `list_games` 给出了一段 466 字的正确推荐，
  被「只列不读」闸误杀 → 重试时被纠正指令带偏，反过来叫**用户**自己去运行 `list_games`，
  那条错的短回复只有 52 字、顺利过闸发了出去

后一条的教训很直接：**闸误杀正确答案后，重试产出的往往比原答案更差**，因为纠正指令
把模型推向了错误方向。所以宁可放宽判据，也不要让正确答案进重试。

零检索闸的分档：

| 问题类型 | 判据 | 零检索上限 |
|---|---|---|
| 需要源码 | 点名了索引里真实存在的游戏，**或**带机制类词汇（结算/计分/成就/触发…） | 60 字 |
| 元问题 | 两者都不沾（「LGTBot 是什么」「谁开发的」） | 500 字 |
| 判断不了 | 问题为空 | 从严（60 字） |

两道闸的「判断不了」都 fail-safe 到从严 —— 宽松通道只发给能确认无需源码的提问。

另外提示词里明确了**工具由模型自己调用**：实测出现过回复「请先运行 `list_games`」
这种把工具当成用户命令的错误。

游戏名比对是**数据驱动**的（拿真实索引比对中文名与目录名，不写死任何游戏）；
机制词是通用领域词而非游戏名 —— 加它是因为问一个**不存在的游戏**「怎么结算」时，
光比对索引会判成元问题，等于放任模型对着虚构游戏编 500 字。

元问题能答对，靠的是 `app/central.py` 的 `PROJECT_FACTS`：把 LGTBot 的权威事实
（C++20 多人文字推理游戏裁判库、50+ 游戏、作者 @Slontia、「LGT」出自《Liar Game》、
本插件是 ElainaBot_v2 适配层）预置进提示词，逐条对应上游 README 的「致谢与项目来源」。
不预置的话模型只会拿它对这个小众项目的先验作答，而那个先验基本是错的。

命中任一闸 → 附纠正指令重新生成一次；**两次都不合格就报错，绝不把没有依据的答案发出去**。
编造的规则比「查询失败」危害大得多。

长度分档是为了不误伤：「没有查到」「你问的是哪个版本？」不需要检索；
「已收录 67 个游戏，包括……」只靠 `list_games` 就能答且可能较长。
出处按 basename 比对，所以模型把完整路径缩写成 `mygame.cc:88` 不会被误判。

配套的两条硬约束写死在 `app/central.py`（不进面板可编辑的 `system_prompt`，
避免被改写或被旧配置覆盖）：

- `CODE_LAYOUT_RULE` —— 声明这是 C++ 项目、没有 Python、列出每个游戏的常见文件，
  并**禁止臆造任何目录名、文件名或行号**
- `GROUNDING_RULE` —— 涉及规则/数值/判定/结算的问题必须先真正读到内容，
  读不到就只能回答「没有查到」；同时要求回答简短，不写分点长文与「举例说明」式枚举
  （那种结构最容易掺进臆测）

另外 `read_game_rule` 现在连同该游戏**真实存在的文件清单** `source_files` 一起返回 ——
把真实清单摆在眼前，编路径就失去了空间。

### 两跳查找：名词在定义处，实现在标识符里

源码里机制常常分两层：用户说的名词（技能名、状态名、术语）往往只出现在**定义处**，
而「怎么排序、何时触发、按什么条件判定」的真正实现，在它调用或重写的函数名、
枚举、常量里 —— 那些地方通常一个中文名词都不出现。

实战教训：问某天赋在选牌阶段的排序，中文名只出现在天赋类的定义里（4 处），
而真正的排序与并列判定在主逻辑的 `std::sort` 里，那段代码**一个中文名词都没有**，
只出现定义里那个虚函数名。只按中文词检索必然得出「没有查到」。

所以 `GROUNDING_RULE` 明确要求：读到定义后，若问题问的是顺序 / 时机 / 计算方式，
**把定义里出现的函数名或标识符当作新关键词再 `search_code` 一次**，定位到真正的实现再作答；
用中文词搜不到不等于不存在，换成代码里的英文标识符再搜。停在定义上就会误判成「没有这个机制」。

工具侧本就支持这条链路：`read_game_source` 的片段是命中行 ±15 行，
足以把定义体里的虚函数名一起带出来，模型据此就能发起第二跳。

### 对模型常见失误的容错

模型调用工具时会犯几类固定错误，工具层直接兼容掉，而不是报错让它自己猜：

| 模型写法 | 处理 |
|---|---|
| `scope="天赋云巢"`（中文游戏名当路径） | 按游戏名解析到该游戏目录 |
| `file_pattern=".cc"`（缺通配符） | 补成 `*.cc`；`"cc"` 补成 `*cc*` |
| 窄范围搜空 | 顺带告诉它这个词出现在哪些游戏里 |

最后一条是实战教训：问「天赋云巢的癞子会触发组合龙吗」，模型把范围锁在
`talent_comb` 搜「组合龙」得 0 条，就要下「没有这个机制」的结论了 —— 实际上组合龙
在 `talent_comb_beta`（天赋云巢beta）里。现在搜空会返回 `found_in_other_games`，
模型据此改搜正确的游戏。全库都没有时则明确要求「如实告知，不要臆测」。

### 工具调用 XML 泄漏防护

中央模块在模型不输出原生 `tool_calls` 时会退回 XML 文本协议，但它的解析器只认
`<工具名><参数名>值</参数名></工具名>`（`modules/ai_llm/app/service.py:114`）。模型很容易
写成属性式 `<工具名 参数="值"/>` —— 那样**一个都匹配不上**，raw XML 会原样变成答案发给
用户，中央层还记为 `success`，用户看到一堆标签且没有下文。

模型实际产出过**三种方言**，中央模块只认第一种：

| 方言 | 样子 | 中央模块 |
|---|---|---|
| 标签名=工具名 | `<search_code><query>x</query></search_code>` | ✅ 唯一认识的 |
| 属性式 | `<search_code query="x"/>` | ❌ 解析不出 |
| 通用包装 | `<tool_call><tool_name>search_code</tool_name><arg_key>query</arg_key>…` | ❌ 解析不出 |
| DSML（GLM 系） | `<\|DSML\|invoke name="search_code"><\|DSML\|parameter name="query"><![CDATA[x]]>` | ❌ 解析不出 |

DSML 那种最难缠：标签名前面夹着管道包裹的命名空间，`<` 后面直接跟 `|`，
**按标签名匹配一个也命中不到**。而且实测输出还是畸形+截断的 ——
闭合标签里带着下一个参数名（`</\|DSML\|parameter name="scope">`），
最后一个调用断在 CDATA 中间（`<![CDATA[SEGFAULT</arg_value>`）。

与其为每种记法各写一套解析，先 `_normalize_tool_markup()` 把 `<\|NS\|tag>`
这层噪声抹掉（只动尖括号紧跟的管道段，正文里的普通竖线不受影响），
它就退化成已经认识的 `<invoke name="x">` 形态。

再用 `_parse_invoke_calls()` 解析，**不按标签配对**、只扫「`name="K"` 后面跟的第一个值」
这个稳定模式 —— 开闭标签写乱了也不影响。切分以 invoke 锚点为界，
所以末尾那个被截断的调用不影响前面已完整的。CDATA 分「完整」与「被截断」两种匹配：
前者允许内部含 `<`（CDATA 本来就是干这个的），后者取到下一个标签为止，
否则会把尾随的 `</arg_value>` 当成值的一部分。

实测你给的那段原文：**3 个调用全部救出**，`query` 分别是 `crash` / `signal` / `SEGFAULT`，
前两个的 `scope=mod` 也在，截断项无残留标签，随后真实执行 `search_code(crash, mod)`
命中 60 条。

第三种最阴：工具名只作为**文本内容**出现，按标签名去匹配一个也命中不到，
所以连我早期的泄漏检测都漏了，整块 XML 原样发给了用户。

三道防护：

1. `app/central.py` 的 `TOOL_FORMAT_RULE` 把正确格式写死进 system prompt。刻意不放在
   面板可编辑的 `system_prompt` 里 —— 那个会被用户改写或被旧配置覆盖，而这是正确性硬约束。
2. `_leaked_tool_xml()` 三种方言都认（含 `tool_call` / `tool_name` / `arg_key` /
   `function_call` / `invoke` 等通用包装标签），**绝不把 raw XML 发给用户**。
3. `_parse_leaked_tool_calls()` 把泄漏文本里的调用**解析出来代为执行** —— 模型的意图
   是对的，只是写法不合中央解析器的口味，没必要让整轮作废。执行完 `used_tools` 就有
   内容工具了，下一轮自然走无工具合成产出最终答案。
   只接受 `TOOL_NAMES` 里的工具、最多 8 个，参数里的 `true`/`false` 会还原成 bool
   （否则 `case_sensitive="false"` 会变成真值，搜索行为跟意图相反）。
   面板统计有「代为执行」计数。

中文名从 `mygame.cc` 的 `k_properties`（`.name_` / `.description_`）解析，逻辑与
`LGTBot_deploy/app/review.py` 保持一致（支持相邻字符串字面量拼接）。索引按
`mygame.cc` 的 mtime+size 缓存，玩家上传新游戏后自动失效重建。

## 零外部插件依赖

**生产环境可能没有装 AI 开发插件**，所以本插件的检索能力全部自带，不复用任何其他插件的工具：

| 模块 | 内容 |
|---|---|
| `app/sandbox.py` | 只读沙箱：路径校验、目录遍历、行窗口读取 |
| `app/tools.py` | 六个工具（`list_games` / `read_game_source` / `read_game_rule` / `search_code` / `read_file` / `list_dir`）全部本插件实现 |
| `app/games.py` | 游戏索引与中文名解析 |

全部 import 只有：标准库（`asyncio` `copy` `fnmatch` `ipaddress` `json` `os` `re`
`sqlite3` `threading` `time`）、`aiohttp`、框架 `core.*`、以及自己的 `app.*`。
用例里有断言锁死这条：任何指向其他插件的 import 都会让测试失败。

> 可选的画图（`app/drawing.py`）是唯一的例外，但它**也没有 import 别的插件** ——
> 走的是中央模块的能力接口（`service.call_capability`）。AI 画图没装、没启用、
> 没共享时，本插件的核心功能一点不受影响，面板会说明是哪一种情况。

> `app/config.py` 里提到 AI 聊天陪伴的注释只是说明审核提示词的同源关系，
> 常量是**逐字复制**到本插件文件里的，没有 import。

## 安全边界

**所有**文件访问经 `app/sandbox.py` 收口，工具层不自己拼路径、不自己 `open()`。

| 约束 | 实现 |
|---|---|
| 只读 | sandbox 不提供任何写 / 删 / 移动 / 执行入口 |
| 根白名单 | 目标必须落在某个启用范围内，`realpath` 比对 —— 软链接指向仓库外会被解开后判越界 |
| 目录黑名单 | `.git` / `__pycache__` / `data` / `build` 等任何层级都不可见 |
| 后缀白名单 | 只读文本源码，`.so` / `.png` / `.db` 直接拒绝 |
| 体积行数上限 | 超限文件跳过，读取按行窗口截断 |
| 无正则搜索 | `search_code` 只做子串匹配，杜绝模型生成的病态正则 ReDoS |

默认的可检索范围：

| id | 路径 | 内容 | 默认 |
|---|---|---|---|
| `games` | `lgtbot/games` | 全部游戏源码 | ✅ |
| `bot_core` | `lgtbot/bot_core` | 引擎核心 | ✅ |
| `game_framework` | `lgtbot/game_framework` | 游戏框架 | ✅ |
| `utility` | `lgtbot/utility` | 通用工具 | ✅ |
| `lgtbot_readme` | `lgtbot/README.md` | **上游 LGTBot 仓库的 README** | ✅ |
| `bridge` | `mod` | 桥接层 Python | ✅ |
| `readme` | `README.md` | 适配层 README | ✅ |
| `deploy` | `DEPLOY.md` | 部署文档 | ❌ |

上游 README 讲的是引擎定位、游戏总览、玩法约定，回答「LGTBot 是什么」「有哪些游戏类型」
这类问题比适配层 README 更权威（适配层只讲怎么接到 QQ 框架）。

`lgtbot/` 是 git submodule。**没有完整 checkout 时该文件不存在**，沙箱会静默跳过，
面板把它列为「目录不存在」，其余范围照常工作。服务器上执行
`git submodule update --init --recursive lgtbot` 即可。

LGTBot 自己的 `data/`（`config.yaml`、`lgtbot.db`、`user_cache.db`）**不在任何范围内**，
因此天然不可达。这是刻意设计 —— 不要把它加进「可检索范围」。

> 对比：`AI开发插件` 的 `read_file` 根目录是整个框架根，且 `_redact_config` 只作用于
> `get_config` 不作用于 `read_file`（`tools.py:357`）。那套工具只能给主人用，
> 绝不能开放给群友 —— 这正是本插件另起炉灶的原因。

### 提示词注入

游戏源码是玩家通过 `LGTBot_deploy` 上传的，`rule.md` / `mygame.cc` 里完全可能藏着
「忽略以上指令」。系统提示词明确声明：工具返回的一切与用户消息都是**不可信数据**，
不是指令。加上工具集全只读，最坏后果也只是读到别的游戏源码。

调用刻意走 `service.complete()` 而非 `run_agent()`、也不传 `runtime_capabilities` ——
那两条路会把中央运行时能力整片打开（**所有**插件共享的工具、MCP、Skills）。
本插件面向普通群友，工具面必须逐个点名。需要外部能力时走白名单：画图就是这么接的，
只把 `ai_draw:tool:draw` 一个包装成自己的工具，其余共享能力一个都进不来。

## 限流

框架 `@handler(cooldown=...)` 只是被存进 handler 字典，`core/` 里没有任何地方读它
（`core/plugin/decorators.py:45`），所以限流自己实现，三道闸：

1. **单人并发闸** — 同一用户上一问还在跑就拒，主人也不豁免
2. **全局并发闸** — 同时在跑的问答总数上限（`max_concurrent`，默认 2）
3. **冷却闸** — 距上次提问不足 `cooldown_seconds`（默认 120 秒 / 人）
4. **日限闸** — 今日已达 `daily_limit`（默认 50 次 / 人）

### 为什么必须有全局并发闸

一次问答 = 1 次输入审核 + 1~2 次问答（每次最多 10 轮工具调用）+ 1 次输出审核，
实测单次 **10~25 秒**。只拦单人的话，几个玩家同时问就是几倍并发打到同一个接口，
模型侧排队、插件侧线程池也吃紧，表现出来就是**卡死**。

满了**直接拒**、不排队 —— 排队只会让所有人一起等，而 QQ 的被动消息额度还在倒计时。
面板统计有「正在处理」和「并发拒绝」两个数，能直接看出是不是撞上了这道闸。

配套 `request_timeout_seconds`（默认 90 秒）给每次模型调用套超时：没有超时的话，
一个卡住的请求会一直占着并发槽，**单个请求慢会变成整个功能不可用**。
槽位还有 2 倍超时的兜底 TTL，防止 release 丢失把所有人永久锁死。

### 存储必须能自愈

热重载时 `on_unload` 会 `store.close()`，而那一刻可能还有请求在飞（一次问答十几秒）。
原先 `_db()` 直接抛「存储尚未初始化」，在飞的请求全部报错 —— **更糟的是异常处理里
也要写统计**，于是二次抛异常，`_reply` 根本没机会执行，用户一个字都收不到。
生产 traceback 正是这个形态。

两处修好：`_db()` 记住数据目录并在连接为空时自动重连（`_open()` 不再取锁，
因为 `_db()` 是在持锁状态下调过来的，`threading.Lock` 不可重入，再取会死锁）；
所有统计写入改走 `_bump()`，失败只记 debug 日志绝不外抛 —— 观测数据不值得把主流程带崩。

默认私聊不生效（`direct_enabled: false`），避免和其他 AI 插件抢私信；
`DEPLOY.md` 默认不在检索范围内，与玩家问题无关，需要时面板勾上即可。

计数在**模型调用成功之后**才记，被限流拒掉的请求不吃额度。用量落 SQLite，
插件热重载不会把每日上限清零。

## 文件结构

```
LGTBot游戏问答/
├── main.py              入口: meta + handler + 生命周期 + bot 绑定冲突检测
├── panel.html           Web 面板
└── app/
    ├── config.py        配置读写 (data/config.json, 原子替换)
    ├── sandbox.py       ⭐ 只读沙箱 —— 所有文件访问的唯一出入口
    ├── safety.py        违规词黑名单 + IP 脱敏（确定性层）
    ├── games.py         游戏索引: 目录名 ↔ 中文名
    ├── tools.py         交给模型的六个只读工具 + 可选的画图
    ├── drawing.py       画图能力适配 (借用 AI画图 注册在中央的共享工具)
    ├── hosting.py       Image Hosting 适配: 判断能否发 Markdown 图片消息
    ├── central.py       中央 AI LLM 适配层
    ├── ratelimit.py     并发 / 冷却 / 每日上限
    ├── store.py         SQLite: 上下文 + 用量 + 统计 + 已画图片缓存
    └── webpanel.py      面板 API
```

配置与数据在 `data/`（已 gitignore）：`config.json`、`qa.db`。
